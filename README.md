# meili-indexer

Наповнює пошук Meilisearch для lartek.com.ua з YML-фіду Horoshop.
Запускається на Railway за розкладом (`railway.json` → cron, раз на 6 год).

## Як працює (безпечне оновлення)

1. Качає фід → **гард #1**: перевіряє, що це XML з `<offer>` (а не анти-бот
   заглушка / HTML / порожньо).
2. Мапить у документи (нормалізація розмірів: `30*52*10` = `30×52×10` = …).
3. **Гард #2**: кількість товарів адекватна (≥ `MIN_DOCS`) і без різкого
   падіння (≤ `MAX_DROP_RATIO`) — інакше оновлення скасовується, живий пошук
   не чіпається.
4. Будує **тимчасовий** індекс `products_build`, заливає туди, перевіряє
   повноту.
5. **Атомарна підміна** (`swap-indexes`): `products` миттєво отримує свіжі дані;
   пошук ніколи не бачить напів-оновлений стан. Старі/зняті товари зникають
   автоматично (щоразу свіжий індекс).

**Fail-safe:** за будь-якої помилки живий індекс лишається старим (стале, але
не зламане). Зламати пошук битий фід не може.

## Приховане поле сумісних моделей (`models`)

Якщо задані `MODELS_API_URL` і `MODELS_API_KEY`, індексатор перед побудовою тягне
`GET /api/export` із `models-api` і додає кожному товару поле `models` (перелік сумісних
моделей техніки). Поле є у `searchableAttributes`, але **немає** у `displayedAttributes` —
тобто товар знаходиться в пошуку по сайту за номером моделі, але сам список ніде не
показується й не віддається в браузер (не копіюється). Одруківки на ньому вимкнені
(точний код). Якщо `models-api` недоступний — індексація йде далі без оновлення цього поля
(fail-safe), живий пошук не ламається.

## Змінні (Railway → Variables)

| Змінна | Призначення | Типово |
|---|---|---|
| `MEILI_KEY` | майстер-ключ Meilisearch (обов'язково) | — |
| `MEILI_HOST` | адреса Meilisearch | вписано в коді |
| `FEED_URL` | URL YML-фіду | вписано в коді |
| `MEILI_INDEX` | назва індексу | `products` |
| `MODELS_API_URL` | домен `models-api` для підтягу сумісних моделей | — (вимкнено) |
| `MODELS_API_KEY` | ключ до `/api/export` (= `IMPORT_KEY` у models-api) | — |
| `MIN_DOCS` | мінімум товарів у фіді (нижче — стоп) | `1500` |
| `MAX_DROP_RATIO` | макс. допустиме падіння кількості | `0.4` (40%) |
| `TG_BOT_TOKEN` | токен Telegram-бота (як у salesdrive-report) | — (вимкнено) |
| `TG_CHAT_ID` | chat_id, куди слати сповіщення | — (вимкнено) |

## Сповіщення в Telegram (heartbeat)

Якщо задати `TG_TOKEN` і `TG_CHAT_ID`, після кожного запуску бот шле:
- ✅ успіх: «пошук оновлено, N товарів (було M), категорій K»;
- ❌ провал/гард: текст помилки + «живий пошук лишився старим».

Так одразу видно, якщо оновлення впало або пропустилось. Без цих змінних
сповіщення просто вимкнені (на роботу індексатора не впливає).

**Де взяти:** `TG_TOKEN` — від @BotFather; `TG_CHAT_ID` — надіслати боту
будь-що і відкрити `https://api.telegram.org/bot<TG_TOKEN>/getUpdates` →
поле `chat.id`.

## Розклад

`railway.json` → `deploy.cronSchedule: "0 */6 * * *"` (раз на 6 год).
Змінити частоту — правити це значення.

## Запуск локально

```
MEILI_KEY=<master> node indexer.js
# або з іншим фідом:  node indexer.js https://.../feed.xml
```

# source-tracker: «Джерело замовлення» з дзвінків Binotel

`source-tracker.js` — окремий cron-скрипт: проставляє в SalesDrive поле
«Джерело замовлення» для заявок, де воно порожнє. Джерело визначається тим,
**на який номер компанії подзвонив клієнт** (різні номери — на різних
майданчиках): скрипт знаходить у журналі Binotel останній дзвінок клієнта
перед створенням заявки і за мапою «номер → джерело» оновлює заявку через
API SalesDrive.

**Fail-safe:** заповнює лише ПОРОЖНЄ поле, вже проставлене джерело ніколи не
перезаписує. Помилка на одній заявці не зупиняє решту.

## Налаштування

1. **Мапа номерів** — скопіюй `source-map.example.json` у `source-map.json`
   і впиши свої номери та джерела (текст опції поля або її id):
   ```json
   { "0671234567": "OLX", "0442223344": "Сайт" }
   ```
   Або задай те саме JSON-рядком у змінній `NUMBER_SOURCE_MAP`.
2. **Змінні** (Railway → Variables):

   | Змінна | Призначення | Типово |
   |---|---|---|
   | `SD_API_KEY` | ключ API SalesDrive (Налаштування → Форми → API) | — (обов'язково) |
   | `SD_DOMAIN` | домен кабінету | `komplektom.salesdrive.me` |
   | `SOURCE_FIELD` | машинна назва поля джерела | `dzereloZamovlenna` |
   | `BINOTEL_KEY` / `BINOTEL_SECRET` | API-ключі з кабінету Binotel | — (обов'язково) |
   | `NUMBER_SOURCE_MAP` | мапа «номер → джерело» (замість файлу) | — |
   | `LOOKBACK_DAYS` | за скільки днів обробляти заявки | `3` |
   | `MATCH_GRACE_MIN` | дзвінок пізніше заявки на ≤ стільки хв ще зараховується | `30` |
   | `TG_BOT_TOKEN` / `TG_CHAT_ID` | сповіщення в Telegram (опційно) | — |

3. **Перший запуск — обов'язково пробний:**
   ```
   SD_API_KEY=… BINOTEL_KEY=… BINOTEL_SECRET=… node source-tracker.js --dry-run --days=7
   ```
   Він нічого не змінює, а показує: приклад запису дзвінка (звірити назви полів),
   опції поля джерела (звірити тексти/id у мапі), список ваших номерів, яких
   немає в мапі, і що саме було б проставлено. Якщо все сходиться — запускай
   без `--dry-run`.

## Розклад на Railway

Це другий сервіс у тому самому репозиторії: **New Service → з цього GitHub-репо**,
у Settings постав **Custom Start Command** `node source-tracker.js` і
**Cron Schedule** (наприклад `15 * * * *` — щогодини). Змінні — у Variables
цього сервісу.
